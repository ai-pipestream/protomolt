## Correction-path implications

The fast starter already has a typed correction fixture in `samples` and an existing schema compiler, prompt renderer, validator and structured generator, as traced in [starter-contract-inventory.md](starter-contract-inventory.md). Its first acceptance case can use the contract's immutable inline text and explicit target descriptor closure/name, with bounded attempts, deterministic validation, semantic support judgment, and a recorded unresolved outcome when support is absent. The data-foundation libraries do not supply a semantic verdict by themselves. `meta.v1` sensitivity, `SensitivityMasker`, and optional search screening govern disclosure; neither means that every returned value is factually supported.

For the representative court case, [OpinionMetadata](../../protobuf/llm/examples/court-decoration/proto/court/v1/opinion_metadata.proto) is an existing `llm.v1`/`validate.v1` form. Four saved rounds contain 315 **per-document/persona** records (45, 90, 90, 90), from Qwen3-14B-int4 and three personas; [round findings](../../protobuf/llm/examples/court-decoration/round-1/FINDINGS-round-1.md) show schema-valid invented dockets, while [round 3](../../protobuf/llm/examples/court-decoration/round-3/FINDINGS-round-3.md) shows `skip_when` allowing valid declarations of incompleteness. The corpus size in the example is background to the experiment, not the count of validated model outputs. The external historical jobs harness used older `SubmitChain` and `ai.pipestream.proto` contracts, so it needs porting before any current regression claim. Its saved job outcomes and timing findings are historical evidence only; this audit did not rerun it or a model.

If a later document-backed correction uses retrieval, its possible dependency chain is intake scope → repo source/parts → parse result → search mapping/chunk/index generation → retrieved source spans → model grounding → validator → support/evaluation → run evidence. The minimal no-provider fixture starts at immutable inline source text and descriptor; it needs no search role, index, or screening pipeline. The mounted search service provides document/chunk IDs and typed stored fields, but a later retrieval design should bind a claim to the exact source version and span before treating a hit as evidence. The optional screening mount and vectorization policy matter if classified text is indexed or embedded.

## Proposed follow-ups for root review

1. **Clarify the inline input binding in Goal 1.** The starter uses immutable inline text. Root will define how the stored input and any projection bind to the offered source in the main specification. A future repo-backed input would need its own version/span policy; an index hit ID alone cannot establish a quotation.
2. **Keep the existing gate distinctions explicit.** Schema validity, source support, and review are separate decisions. A `skip_when` incomplete result is a valid declaration for review, not an accepted answer. Screening/taxonomy checks apply only when configured on a relevant path; they are not prerequisites for the minimal starter.
3. **Carry provenance at the point it matters.** The compiled import closure/fingerprint, resolved message name, named workflow version, and chosen model already appear in the main contract work. If later retrieval or screening is selected, specify source version, policy/model version, and index generation in that design. No new proto field is requested by this audit.
4. **Add the court regression to the later backlog.** Port the saved example/harness to current contracts, then test fabricated docket, copied exemplar, incomplete with reason, unsupported citation, and an externally completed job. A screening refusal belongs in that later path only if screening is configured. This is separate from Goal 1's small contact fixture and does not make external model, corpus, registry, or GPU availability a prerequisite for the no-provider gate.
